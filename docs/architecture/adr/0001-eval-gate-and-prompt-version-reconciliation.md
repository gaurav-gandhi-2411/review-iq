# ADR 0001: Eval Gate, Prompt Version, and Tiered-Routing Disclosure Reconciliation

**Status:** Accepted
**Date:** 2026-07-30
**Scope:** Wave 1 Section A ("Truth reconciliation") of `docs/specs/wave1-commercialization.md`.
Verification gates addressed: #3 (no un-sourced accuracy figure on any surface), #4 (every
metric carries n + 95% CI), partially #5 (moved stale/contradictory claims into this ADR or
inline corrections — the site's separate "Known gaps" callout is untouched, out of scope
here). Gates #1/#2/#6–#12 (domain consolidation, adversarial RLS, PII redaction, cost
telemetry, corpus pipeline, logo) are explicitly **not** addressed by this ADR or this wave
section.

## Context

Three independent, verified-live contradictions existed simultaneously across
`README.md`, `site/index.html`, and `site/docs/index.html` as of 2026-07-30:

1. **Gate threshold.** `README.md` stated "CI breaks if accuracy drops below 85%" and a
   results table with "Gates: overall ≥ 85%, per-language ≥ 80%." The real gate, in code,
   is `PASS_THRESHOLD = 0.83` / `PER_LANG_THRESHOLD = 0.80` (`eval/runner.py`), lowered from
   0.85 on 2026-06-14 with this rationale already in a code comment: *"free-tier vernacular
   routing keeps hi/hi-en on the small model (cap-immune) at a ~1% overall cost while every
   per-language gate still holds >=80%."* `site/index.html` already had the correct 83%/80%
   figures — the demo page and the README had drifted apart, each independently hand-typed.
2. **Prompt version.** `README.md`'s example JSON response and a Roadmap bullet referenced
   `v2.0`/`v2.1`. Production is `v2.3` (`app/core/prompts/__init__.py`, confirmed via a live
   `/demo/extract` call returning `"prompt_version":"v2.3"`). The version bumped
   v2.0 → v2.1 → v2.3 across three separate prompt-tuning passes with no corresponding
   README update at any of them — a repeated process gap, not a one-off typo.
3. **Tiered-routing disclosure.** A Roadmap bullet said "tiered routing default remains OFF
   pending 85% overall gate." `enable_tiered_routing` defaults `True`
   (`app/core/config.py`), and Cloud Run's deployed env vars do not set
   `ENABLE_TIERED_ROUTING` at all (confirmed via `gcloud run services describe`), so the
   code default applies: tiered routing is live in production right now, serving real
   traffic. `docs/specs/wave1-commercialization.md`'s own "current state" table (written the
   same day as this ADR) repeats the same stale "shipped but default OFF" claim — this
   was a repo-wide belief, not an isolated README bug.

All three shared one root cause: **numbers were hand-typed into prose, with no single
source of truth and no mechanism to catch drift.** `eval/results.json` existed but was a
point-in-time snapshot (last regenerated by commit `13a4422`, 2026-07-06) that nothing
diffed against, and nightly `eval.yml` runs only post to Slack + upload a CI artifact —
they never commit back to the repo.

**A fourth issue surfaced during this work, not previously known:** because
`enable_tiered_routing` defaults `True` with no CI override, `eval.runner`'s "direct"
path (`run_single`, no `--routed` flag) calls `extract_with_llm()`, which **itself**
invokes the tiered router internally whenever routing is enabled. A same-cassette
comparison — `python -m eval.runner` vs `python -m eval.runner --routed` against the
current cassette set (prompt v2.3) — produced **byte-identical** overall and per-language
scores (83.8% / 86.2% en / 80.9% hi-en / 80.7% hi). The "direct (unrouted) CI gate" and
"routed measurement" that the commercialization spec assumes are two distinct numbers are,
under the current config, the same number. The historical v0.5.0 row showing 84.4%
routed vs a different direct-mode figure predates prompt v2.3 and used different fixtures
— it is not a live counter-example, just a stale one.

A fifth, smaller issue: `eval/authenticity/runner.py` has no cassette-replay support
(unlike `eval/runner.py` — `GroqProvider` itself is cassette-aware, but no cassette was
ever recorded for the authenticity prompt). Attempting `EVAL_CASSETTE_MODE=replay` against
it fails loudly on all 40 fixtures ("No cassette for key ..."). This session's constraints
forbid live LLM calls, so the authenticity numbers in this reconciliation are a
**reconstruction** from the last published point estimate (precision/recall/F1 = 1.000,
n=40, 19 genuine / 14 suspicious / 7 likely_fake — algebraically forcing tp=21, fp=0, fn=0,
tn=19), not a fresh measurement. This is disclosed via a `provenance_note` field in
`eval/results/authenticity_latest.json` and inline in the README, not silently presented as
current.

## Decision

1. **Keep the 0.83/0.80 gate as-is; document it, don't relitigate it.** No new evidence
   changes the 2026-06-14 rationale. Silently re-tightening it back to 0.85 now, with no
   measurement behind the change, would repeat the exact anti-pattern this wave exists to
   fix (spec §6: "never widen a tolerance, lower a gate ... to make a check pass" — the
   inverse, quietly raising it back for optics without a measurement, is equally dishonest).
2. **`eval/results/latest.json` (extraction) and `eval/results/authenticity_latest.json`
   (authenticity) are the single sources of truth.** Both now carry `prompt_version`,
   `mode`, `generated_at`, `git_sha`, and a 95% Wilson confidence interval on every reported
   score (`eval/wilson.py`; the existing `eval/results.json` path is kept unchanged for
   `eval/report.py` / `eval/slack_notify.py`, which already depend on that exact filename).
3. **`README.md`, `site/index.html`, `site/docs/index.html`, and `eval/README.md` render
   their metrics tables from that JSON**, inside `<!-- METRICS:START:<name> -->` /
   `<!-- METRICS:END -->` blocks owned by `scripts/render_metrics.py`.
   `scripts/check_no_hardcoded_metrics.py` fails CI on any percentage-shaped number near an
   accuracy/gate/threshold keyword that sits outside such a block (or an explicitly
   human-reviewed `<!-- METRICS:HISTORICAL -->` block — see below). Both scripts are wired
   into `ci.yml`.
4. **Historical numbers are preserved, not rewritten, but explicitly marked.** Frozen
   past-release rows and superseded Roadmap bullets (e.g. "Phase 2.0b shipped with an 85%
   gate," "hi-en prompt v2.1 shipped in Phase 2.0c") stay as dated historical fact — rule
   53's "commit messages/docs name what didn't work, not just what shipped" extends to not
   revising history. They are wrapped in `<!-- METRICS:HISTORICAL -->` markers (exempted
   from the scanner, but never regenerated) and annotated with what has since changed,
   so a reader isn't misled into thinking history describes the present.
5. **Tiered-routing disclosure: report it as ON, with the caveat that direct/routed
   currently coincide.** Rather than picking one of "84.4% routed" or "83.8% direct" and
   presenting it as *the* number, the README states the current direct-mode CI gate number
   (83.8%), discloses that tiered routing is on by default in production and in this eval
   run, and states plainly that a same-cassette routed comparison produced an identical
   result today — with a pointer to this ADR for the underlying reason (config default,
   not a router bug). It does not claim direct and routed will always match; that would be
   an unfalsifiable claim about future behavior this ADR cannot support.
6. **Authenticity metrics are disclosed as a reconstruction, not a live measurement**, via
   an explicit `provenance_note` and a "KNOWN GAP" flag: `eval/authenticity/runner.py`
   needs cassette-replay support (mirroring `eval/runner.py`) before its numbers can be
   regenerated in CI. This is left as a follow-up, not silently worked around.

## Consequences

**Positive:**
- One machine-checked source of truth for every accuracy claim on README/site; a future
  prompt or fixture change that regenerates `eval/results/latest.json` and runs
  `scripts/render_metrics.py` will automatically keep every surface in sync, and CI fails
  loudly (not silently) if someone hand-edits a number instead.
- Every reported score now carries n and a 95% CI — no more bare `1.000`.
- The "direct vs routed" ambiguity is now documented in code (`write_results()`'s
  docstring) and in this ADR, instead of being silently lost the next time someone reads
  the old README claim at face value.

**Negative / residual risk:**
- `scripts/check_no_hardcoded_metrics.py` is a regex heuristic (documented in its own
  docstring), not a parser. It required a hand-curated exclusion list
  (`benchmark/`, `ops/runbooks/`, `eval/fixtures/`, `eval/data/`, `eval/report.md`,
  `plan.md`, `plan_v1.md`, `PROMPTS.md`, `spec.md`, `review-iq-closeout-roadmap.md`) to
  avoid failing CI on this repo's own pre-existing historical documentation. That list
  needs periodic review — a genuinely new hardcoded metric landing inside one of those
  excluded paths would not be caught.
- `eval/results/authenticity_latest.json` is a reconstruction, not a fresh measurement.
  Until authenticity cassettes are recorded, this number cannot be regenerated in CI and
  relies on the accuracy of the last published figure.
- The Wilson interval applied to `eval/runner.py`'s field-averaged fixture scores (as
  opposed to strictly binary trial outcomes) is an approximation, explicitly documented as
  such in `eval/wilson.py`. It is directionally informative (small eval sets get wide
  bands), not a statistically exact interval for a mean-of-continuous-scores estimator.
- This ADR does not touch Sections B–H of the commercialization spec (relabeling fixture
  provenance, DNS/domain consolidation, logo/visual identity, PII redaction, adversarial
  RLS testing, cost telemetry, corpus pipeline) or the site's separate "Known gaps"
  disclosure box — those are explicitly out of scope for this change.

## Alternatives considered

1. **Raise the gate back to 0.85** to match the README's (wrong) claim instead of fixing
   the README. Rejected — no measurement supports 0.85 today; the 2026-06-14 decision to
   lower it was evidence-based (per-language buckets still ≥80% at ~1% overall cost from
   free-tier vernacular routing) and nothing has changed that calculus. Silently
   tightening a gate to match stale marketing copy, with no new data, is the same class of
   dishonesty as silently loosening one to pass a check.
2. **Disable tiered routing** so "direct" becomes a genuinely distinct measurement again.
   Rejected — this is a production serving-behavior change (blast radius: real traffic,
   real cost/latency trade-offs), entirely outside this section's scope (docs + CI only),
   and unsupported by any evidence that routing is causing a problem. The honest fix is
   disclosure, not silently changing what's live to make a narrative cleaner.
3. **Re-run the authenticity eval live against Groq** to get a fresh, verifiable number.
   Rejected for this session — live LLM calls were explicitly out of scope (must stay
   $0 / CI-cassette-replay-safe); recorded instead as a named follow-up (record
   authenticity cassettes) rather than silently reusing the old number without saying so.
4. **Bootstrap resampling instead of a Wilson interval** for the eval scores. Considered —
   would be more statistically appropriate for a mean of continuous per-fixture scores.
   Rejected for now: Wilson is what the task specified, is simpler to implement and audit,
   and is explicitly documented as an approximation rather than oversold as exact. Revisit
   if a decision ever hinges on the precise shape of the per-fixture score distribution
   rather than "is this gate result within noise."
