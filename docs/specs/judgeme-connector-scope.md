# Judge.me connector: scope and remaining build days (S21)

**Target user:** a Shopify seller who collects reviews with Judge.me and wants them classified without a CSV export.
**Pain point:** reviews live in Judge.me; getting them into Samidha today means manual CSV upload.
**Success metric:** a seller pastes two credentials and sees their last 90 days of reviews analysed within minutes, then new reviews flow in daily; zero duplicates on re-sync.
**Who pays:** the seller, on the existing tiers. No new price.

## Facts about the Judge.me API (BELIEVED: from the official help article as quoted in a search, plus third-party guides; the live API docs are JavaScript-rendered and could not be fetched)

- Two credentials: `shop_domain` (myshopify.com form) and a private `api_token`. The private token can
  read reviews and, per the help article, has read/write access, so it must be stored like a secret.
  The public token cannot read reviews.
- `GET https://api.judge.me/api/v1/reviews` with `api_token`, `shop_domain`, `per_page` (max 100), `page`
  and filters (`product_id`, `rating`, `published`, `reviewer_id`, `reviewer_email`).
- The private token cannot be regenerated by the seller; they must contact Judge.me support. Our
  disconnect flow therefore cannot rotate it for them; we delete our copy and say so.
- Rate limits: not publicly documented. A third-party guide advises treating them as unknown and backing
  off; 429 responses exist. Design for back-off, not for a number.
- Webhooks: third-party sources list `review/created`, `review/updated`, `review/published`,
  `review/unpublished`, unsigned (validate `shop_domain` in the payload). Not verified against Judge.me.
  Plan tier required for API or webhooks: not found. **Unknown; ask a Judge.me account holder.**

## Design (reuses what exists)

| Piece | Reuse | New |
|---|---|---|
| Credential storage | `shopify_installations` pattern: Fernet-encrypted token column, `revoked_at`, RLS by org | table `judgeme_installations` plus migration with postconditions and an undo case |
| Ingest | existing durable ingest queue (`batch_job_rows`, `ingest-tick`) and `app/api/v2/ingest.py` | adapter mapping a Judge.me review to the ingest row (text, rating, date, product, external id) |
| Dedup | `review_id` column (20260619000001) | external id = Judge.me review id, unique per org |
| Sync | scheduler tick | poller: backfill by `page` descending date to 90 days, then incremental by newest id/updated time every N hours; back-off on 429 |
| UI | BFF connect screens used for Shopify/Google | a "Connect Judge.me" form (domain + token) with the loading, empty and error states (rule 15a) |

## Risks and open questions

1. No Judge.me account is available to this session. Everything above about the API is unverified
   against a live store. First task is GG creating a free Judge.me test store (free plan exists; the
   API plan requirement is the thing to check).
2. `shop_domain` is user input that becomes part of an outbound request: validate against
   `^[a-z0-9-]+\.myshopify\.com$` before any call (SSRF).
3. A private read/write token is more power than needed; the UI must say what we do with it.
4. Judge.me reviews carry reviewer emails: PII. Store only what classification needs; do not persist
   reviewer email.
5. Not started: nothing is built. Run after the engine's E2 report, as sequenced in the brief.
