# Privacy Policy

**Product:** Samidha Reviews ("the Service"). **Operator:** Gaurav Gandhi ("we", "us", "our").
**Effective date:** `[TODO: GG to set on publication]`

This Policy explains what data the Service collects, how it is processed, where it goes, how
long it is kept, and what rights you (or, if you are a business customer, your own end-customers
whose review text you submit) have over it. It applies to the hosted Service at
`api.samidhareviews.xyz` (production Cloud Run host as of this drafting:
`review-iq-ajjrytb3na-el.a.run.app`) and the account/signup surfaces.

**Two categories of person this Policy speaks to:**

- **Customer** — the business/organization that signs up for an API key and sends review text to
  the Service.
- **End-customer** — the person who wrote a review that a Customer submits to the Service (e.g. a
  Customer's own shopper). If review text contains an end-customer's personal data (name, email,
  phone number, order ID), the Customer is the **data controller** for that data, and we act as
  the Customer's **data processor** — see the [DPA template](./dpa-template.md).

## 1. What data we collect

| Category | Examples | Source |
|---|---|---|
| **Review text** | The raw text submitted to `/v2/extract`, `/v2/ingest/csv`, `/demo/extract`, etc. May contain end-customer PII (names, emails, phone numbers, order/invoice IDs) if the Customer's own review data includes it. | Submitted by the Customer via the API |
| **Structured extraction output** | Sentiment, topics, pros/cons, competitor mentions, urgency signal, authenticity score/label/flags. | Generated by the Service from review text |
| **Account/signup data** | Email address (via Supabase magic-link auth), organization slug, API key metadata (prefix, quota, creation/revocation timestamps — never the raw key itself after initial display). | Provided at signup |
| **Usage/API logs** | Request timestamps, endpoint, response status, latency, `org_id`, structured log fields (`latency_ms`, `provider`, `model`, `tokens_in`, `tokens_out` where applicable). Raw review text is **not** written to structured logs beyond what's needed to serve the request. | Generated by the Service on each call |
| **Authenticity audit records** | `org_id`, a SHA-256 hash of the review text (**not** the plaintext), score, label, flags, timestamp. | Generated when authenticity scoring runs (`authenticity_audits` table) — see `SECURITY.md` §10, `docs/compliance.md` |
| **Corrections** | User-submitted field corrections to extraction output, scoped to an allow-listed set of fields. | Submitted via `POST /v2/corrections` |

We do not collect payment information as of this drafting (no billing integration exists — see
`plan.md`'s Wave 2 scope). This section will be updated when a payment processor is introduced.

## 2. How data is processed

1. **PII redaction before egress.** Review text is passed through a sanitizer
   (`app/core/sanitize.py`) before being sent to any LLM provider. As implemented today, the
   sanitizer performs **destructive redaction** — it replaces detected emails, Indian and common
   international phone number formats, and credit card numbers with `[REDACTED]` placeholders.
   This is a one-way redaction, not a reversible tokenization scheme (a reversible token map is a
   stated future goal in the Wave 1 spec but is **not yet implemented** — this Policy describes
   current behavior only). `[TODO: update this section if/when reversible tokenization ships.]`
2. **LLM extraction.** The (redacted) review text is sent to **Groq** (primary inference
   provider, Llama 3.3 70B / 3.1 8B models) to generate the structured extraction and authenticity
   signal. See [`sub-processors.md`](./sub-processors.md) for what Groq receives and Groq's own
   data-handling commitments. A configurable secondary/failover provider may also process review
   text, gated by a `trains_on_input` check that unconditionally blocks any provider that trains
   on customer input (`assert_privacy_safe()` in `app/core/llm.py` — see `SECURITY.md` §3).
   Google Gemini is excluded from the customer-data (`/v2`) path entirely.
3. **Storage.** Extraction output, authenticity audit records (hashed review text only, not
   plaintext — see §1 table above), account data, and usage records are stored in **Supabase
   Postgres**, isolated per organization via Row-Level Security (RLS) — see
   `docs/data-ownership.md` for the isolation model and [`sub-processors.md`](./sub-processors.md)
   for what Supabase, as our database/auth sub-processor, has access to.
4. **No cross-tenant use.** No Customer's data is pooled into an aggregate corpus, shared model,
   or cross-tenant analysis without that Customer's explicit, revocable opt-in — see
   `docs/data-ownership.md` §"Cross-tenant data use" for the (currently unimplemented) consent
   design that would gate any such future use.

- **While your account is active:** review text, extraction output, authenticity audit records
  (hashed), and usage records are retained for the life of the account — there is no automatic

## 5. Your rights

Depending on applicable law (GDPR for EU-connected data, DPDP Act 2023 for India-connected data —
see [`compliance-posture.md`](./compliance-posture.md)), you may have the right to:

- **Access** the data we hold about your account and your organization's stored review data —
  available today via `GET /v2/dataset` and `GET /v2/dataset/export?format=jsonl`
  (`docs/data-ownership.md`).
- **Delete** your account and all associated data — available today via the self-service
  `DELETE /account` flow (type-to-confirm) — see
  [`data-retention-and-deletion.md`](./data-retention-and-deletion.md).
- **Port** your data — the JSONL export above is designed to be a stable, self-describing format
  for this purpose.
- **Correct** extraction output you believe is wrong — via `POST /v2/corrections`
  (`docs/data-ownership.md` §"Corrections discipline").
- **Object to or restrict** certain processing, where applicable law grants that right.

**If you are an end-customer** (i.e. you wrote a review that a Samidha Reviews Customer submitted
to the Service, and you are not yourself a Samidha Reviews account holder): requests about your
personal data should generally be directed to the Customer (the business you reviewed), who is
the data controller. We support Customers in fulfilling such requests as their processor — see
the [DPA template](./dpa-template.md).

To exercise any of the above rights directly against us (e.g. as an account holder), contact:
`privacy@samidhareviews.xyz` — see also [`compliance-posture.md`](./compliance-posture.md)'s
DPDP grievance officer requirement, which is a related but distinct contact (same mailbox,
different regulatory role).

## 6. Security measures

See `SECURITY.md` in the repository for the full, current technical security posture (PII
redaction, prompt-injection defenses, argon2id API key hashing, Postgres RLS tenant isolation,
quota enforcement, secret management). A summary relevant to this Policy:

- Review text is redacted for common PII patterns before being sent to any LLM provider.
- All tenant data is isolated at the database layer via Row-Level Security, not application logic
  alone.
- API keys are never stored in plaintext (argon2id hashes only).
- Secrets are held in Google Cloud Secret Manager, not in source code or environment files.

## 7. Children's data

The Service is intended for business use (Customers submitting their own end-customers' review
data) and is not directed at children. We do not knowingly collect personal data directly from
children. If review text submitted by a Customer happens to identify a minor (e.g. a product
review mentioning a child), that data is handled under the same controller/processor terms as any
other end-customer data in the [DPA template](./dpa-template.md).
